假设一名数字员工在夜里处理了一批客户资料，第二天，没人能说清它读过哪些数据、调用过什么系统，也不知道某个判断为什么被写进业务流程。这样的 Agent 即使能力很强，也无法进入金融生产环境。

金融业引入 Agent，要同时处理四件彼此牵连的事：模型能不能理解金融业务，系统怎样限制它的行为，真人与数字员工如何分工，以及数字员工上线后由谁管理。如果只实现其中一层，往往是模型能演示、流程接不住，或者业务愿意尝试、治理不敢放行。

## 01 金融大语言模型底层搭建逻辑

### 金融能力要按领域拆开评测

通用模型知道金融概念，却未必熟悉当地法规、产品条款和消费者情境。国泰金控圆桌研讨中介绍的金融大语言模型工作涉及约 20 家银行，知识范围被拆成金融知识、法规合规、授信风险和财富管理四个领域。当地使用的繁体中文、台湾法规、金融商品及消费者情境，也被纳入适配与评测目标。这样拆分一方面，建设团队能看见模型究竟在哪类知识上失分，不会被一个总分掩盖；另一方面，法规或产品变化时，可以只更新相关材料和题集，不必把整个模型能力重新描述一遍。

圆桌分享提到约 4,500 道评测题，题目偏向申论式作答，评测并非只看答案对错，还会看推理步骤、领域得分、权重和零容忍项。法遵、消费者权益或金额控制等题目一旦触发红线，模型需要回到训练环节再测。

| 评测对象 | 主要检查什么 | 应保留的证据 |
| --- | --- | --- |
| 领域知识 | 概念、产品与制度是否掌握 | 分领域题集、知识版本、通过率 |
| 推理过程 | 结论是否经过合理步骤 | 标准解题过程、步骤得分、失败样本 |
| 风险红线 | 严重错误能否稳定拦截 | 零容忍清单、误放记录、复测结果 |
| 本地适配 | 语言、法规和消费情境是否匹配 | 地区化题集、制度版本、专家复核 |
| 工具执行 | 调用系统时是否遵守权限和流程 | 权限拒绝、回滚、幂等与审计测试 |

与开放式向外检索的 RAG 作对比，金融大模型方案强调先让模型读取指定知识，再通过考试检查掌握程度。在生产系统里，模型能力评测和任务发生时的检索并不冲突：模型负责金融概念与推理，检索层提供仍然有效的制度和产品知识，业务系统给出客户、合约及交易的当前状态。

企业专属的上下文在讨论中被称为 Enterprise IQ。它包括内部核保规则、组织与岗位关系、客户历史、产品状态、制度版本和外部信号。模型必须按任务取得这些信息，并知道资料来自哪里、何时生效、谁有权查看。金融知识可以相对稳定，客户余额、理赔状态或授信额度却不能靠参数记忆，也不适合混进一份长期对话记录。

圆桌以一家拥有数百套系统的银行为例，员工完成一项业务可能要登录多个入口。Agent 只连到其中一套系统，就无法核对完整状态，更不能把结果写回原流程。接口接通以后，同一客户、产品或合约在不同系统里的标识还要对齐，资料冲突时也要有可信来源和处理规则。

## 02 金融业 AI 治理框架搭建思路

### 治理对象要落到身份、权限、流程和记录

Agent 一旦可以读取客户信息、选择工具并执行操作，治理就不能只检查它最后说了什么。圆桌给出的几个基本对象很具体：独立身份、职责、权限、主管或指导者，以及工作记录，对应谁在行动、被允许做什么、由谁批准、出了问题怎样追溯。

独立身份使审计人员能区分真人与 Agent 的操作。职责要写到具体任务，不能用“万能助手”代替岗位说明。所有数据访问和工具调用经统一权限入口控制，系统才能在一个地方执行最小权限、时段限制、金额限制和紧急停用。工作记录保存最终答案，还包含输入来源、当时读取的数据版本、模型与工具版本、关键判断、调用动作、人工审批和业务结果。

### Human in the loop/人工守在不可逆节点之前

找到业务流程中的不可逆节点，并在动作发生前安排有权人员确认。

不可逆不只指数据库无法回滚，信贷拒绝已经影响客户，错误投资建议已经送达，理赔决定已经改变权益，大额支付已经发出，即使后台可以改值，业务影响也很难消除。人的确认还应覆盖资料冲突、异常金额、模型低信心和超出职责等情况。

| 任务动作 | 常见风险 | 合适的控制方式 |
| --- | --- | --- |
| 查询制度、汇总资料 | 信息过期、遗漏来源 | 自动执行，显示来源和有效期 |
| 起草报告、合约初审 | 表述偏差、条款漏检 | Agent 起草，员工复核后使用 |
| 更新可撤回的内部状态 | 写错字段、重复执行 | 权限校验、规则检查、操作后抽检 |
| 影响客户权益或资金 | 消费者损失、合规事故 | 执行前由有权人员确认 |
| 超出既定边界 | 新型风险、责任不清 | 停止执行并升级给主管 |

法遵和风险人员要在设计工作流时介入。由中央团队设置身份、权限、日志、数据保护等共同标准，业务部门再为核保、财富管理、客户服务等场景确定业务规则和人工节点。

权限开放跟着证据走。第一版可以只读或只生成草稿，运行记录稳定后再开放可撤回的写操作。每次扩大权限，都要写清新增动作、评测门槛、批准人和回退方式。

业务责任不能因为采用 Agent 而被转移，具体法律责任仍要依据适用法规和机构内的职责安排确定。治理框架的作用，是让责任链能被识别、执行和复盘。

## 03 数字员工与人协同的组织框架

### 先划清三类工作，再安排岗位

数字员工的工作边界设计，可以划分为三类任务：Agent 可以独立处理的任务，需要升级给真人的任务，以及必须由真人作最终判断的任务。划分需要业务、IT、数据、法遵、风险与一线专家共同完成，单靠技术团队很难判断某个动作会怎样影响客户和现有流程。

| 角色       | 在人机协作中负责什么                |
| -------- | ------------------------- |
| 业务负责人    | 确认问题是否值得做，承担业务结果与资源决策     |
| 产品经理     | 拆分工作链，划定自动处理、人工升级和最终判读的边界 |
| IT 与数据团队 | 连接系统，管理数据质量、工具运行和技术回退     |
| 法遵、风险与资安 | 把红线、权限和审计要求写进流程           |
| 一线业务专家   | 提供判断规则、案例与异常样本，复核复杂结果     |
| 数字员工主管   | 审批权限，查看运行记录，处理升级、停用和再训练   |

组织需要为知识整理留出正式工时，业务专家把经验写成 Agent 可执行的规则、样本和例外处理，同时说明哪些经验是个人习惯，哪些可形成机构认可的制度。

员工还要学会判断什么时候可以用 AI，什么时候必须复核。这是新的能力缺口，而非简单的工具培训，持续演练更有用：员工提交真实任务，记录哪里需要补资料、哪里误用了答案，再把这些失败样本交回评测和企业上下文建设。

### KPI 衡量人机协作后的业务结果

数字员工生成了多少内容、节省了多少单步时间，并不能说明整条流程是否变好。三类评测观察面：风险守门、服务价值和端到端流程优化。风险面要看红线误放、误报、越权尝试和人工接管；服务面关注客户等待、一次解决率，以及真人能否把时间留给沟通与判断；流程面则看整体周期、返工、异常积压、成本和最终业务结果。

管理者要把数字员工纳入团队复盘，但不能照搬真人员工的件数考核。Agent 可以快速生成大量内容，同时把复核压力推给后面的人。KPI 应落在人机协作完成后的结果，并同时计入维护知识、权限、题库和运行监控的成本。

## 04 数字员工落地与管理规则

### 把上线改成入职

“让数字员工入职”，而不仅仅是“部署 Agent”。员工入职时有工号、岗位、主管和系统权限，工作会留下记录，调岗或离职后权限会被调整或回收。数字员工也需要一份贯穿全生命周期的治理档案。

档案至少要覆盖八项内容：独立身份、岗位职责、可用技能、数据与系统权限、业务主管、记忆规则、工作记录，以及暂停和退役机制。版本升级、岗位调整和权限变化都要进入档案，避免同一个名字背后已经换了模型、工具或数据范围，管理者却仍按旧能力判断。

### 记忆和技能也要设边界

国泰分享的实作经验提到两个在运行后容易暴露的问题：记忆污染和技能过载。

记忆不能简单理解为保存得越多越好。客户信息会变，临时判断可能只适用于一笔业务，员工的纠正也未必已经获得制度确认。如果这些内容混在长期记忆里，Agent 会把过期状态和未经确认的经验带进下一次任务。管理规则要说明哪些内容可以写入、由谁确认、保存多久、属于客户事实还是工作偏好，以及怎样更正和删除。涉及个人信息时，还要依据适用的数据保护要求限定用途和保存范围。

技能过载发生在工具选择环节。一个 Agent 同时挂载大量功能，名称和用途又互相重叠，规划时可能反复选择工具，看上去一直在工作，实际没有推进任务。岗位职责越清楚，需要加载的技能越少。每个技能还要有明确的输入输出、权限范围、超时和失败处理，排障时才能分清问题出在模型选择、工具执行还是业务数据。

### 从高价值、低风险场景开始

起步场景要能产生业务结果，第一版权限也要收得足够窄，错误能够发现和恢复。适合先做的通常是资料查询、内部摘要、报告草拟和规则明确的辅助审查。链路完整性很重要：Agent 可以只负责一段，但任务要有清楚的入口、异常出口、人工接管和系统写回。

第一轮运行时，员工处理全部异常，团队积累失败样本、误报、越权尝试和人工修改。证据稳定后再扩大权限，每次只增加一类动作。引入多 Agent 协作后，调用链要保留原始身份和授权范围，上游 Agent 无权执行的动作不能借下游工具绕过。

长期运行可以维护两本账。业务账记录客户等待、流程周期、返工、风险损失和运营成本怎样变化；治理账记录 Agent 看过什么、做过什么、谁批准、哪里失败、谁作了最终判断。前者决定项目是否值得继续，后者决定权限是否可以扩大。
